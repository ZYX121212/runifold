# Runifold 在 Agent 技术演进中的定位与路线建议

研究截止 2026 年 10 月 21 日。代码基线为工作区 0.10.1，HEAD fbe9092，包含尚未提交的上下文管理、模型请求调度及 OpenAI 协议适配工作。以下能力判断针对当前源码，不代表已发布版本或生产验收结果。

Runifold 值得继续发展的方向，是为 Rust 应用提供可控制、可恢复、可验证交付的 Agent 运行时。模型与厂商平台越来越能承担规划、工具编排和长任务；应用仍需决定任务的权限范围、真实提交状态、交付证据，以及失败后怎样继续。Runifold 的现有内核与这些问题吻合，但差异化需要通过完整应用证明。

下一阶段应围绕两个参考应用收敛：一个持续研究并产出带来源结论的助手，一个能暂停审批并核对外部操作结果的业务助手。先建立同任务比较和故障验收，再决定哪些重复需求进入公共 API。更广的 Provider 覆盖、通用 Swarm、自研沙箱和训练引擎暂不进入主线。

## 一 技术变化与产品判断

### 厂商正在托管更多 Agent 行为

OpenAI 当前官方资料区分了托管 Codex harness 的 Agents API、应用内运行的 Agents SDK，以及直接控制模型的 Responses API。Gemini Interactions API 则提供后台任务、状态查询和流式重连，Deep Research 仍标为 preview。它们证明厂商已向执行与状态管理延伸，不能据此认定跨厂商功能等价或可无损迁移。[OpenAI Agents](https://developers.openai.com/api/docs/guides/agents)、[Gemini 后台执行](https://ai.google.dev/gemini-api/docs/background-execution)、[Gemini Deep Research](https://ai.google.dev/gemini-api/docs/deep-research)。

Anthropic 的 Managed Agents 将 session、harness 和 sandbox 分离，并举例说明旧模型需要的上下文补丁可能在新模型上成为负担。这支持一个架构判断：应长期稳定的是身份、权限、提交、预算与生命周期契约；规划、摘要、工具选择和模型审查需要能够替换。[Managed Agents](https://www.anthropic.com/engineering/managed-agents)。

因此，Runifold 应同时支持宿主控制的规范 Agent 路径，以及在边缘接入远程任务的可能性。远程任务要暴露提交、查询、等待、取消与结果不明的状态，不能把其内部不可见的操作伪装成本地可审计工具调用。接入之前，还要确认宿主能在什么位置真正执行权限与数据外发控制。

### 长上下文正在变成主动的信息访问问题

RLM 将大输入保留在外部环境，允许模型通过程序查看、拆分和调用子模型，展示了超出单次上下文窗口的处理方式；作者也承认子调用成本与防护机制仍有缺口。后续 SRLM 实验则发现，不少收益来自程序化访问与搜索，递归本身并非始终必要，部分短上下文任务会因递归退化。[RLM](https://arxiv.org/html/2512.24601)、[SRLM 方法与消融](https://arxiv.org/html/2603.15653v1#S3.SS6)。

对 Runifold，更有价值的通用能力是保留原始材料、按引用读取、限制返回量、解释上下文取舍，并让子调用共享预算与取消。RLM 可以成为参考应用中的一种策略，不宜变成新的默认执行引擎。来源存在、来源被读取、来源支持某结论，是三个不同状态。

OpenAI 的工具搜索允许延迟加载工具定义；Programmatic Tool Calling 允许模型编写程序组合工具。官方仍建议对敏感写入默认使用直接调用，以保留清楚的授权边界。[工具搜索](https://developers.openai.com/api/docs/guides/tools-tool-search)、[程序化工具调用](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)。

Runifold 工作区已包含相关 OpenAI 编解码与字段适配。接下来需要验证的是：发现工具不会扩大授权，程序内部每次调用都经过同一权限、Effect、预算和审计路径，且大型中间结果能够保留为引用。协议可传输某字段，并不自动证明应用层的完整安全语义。

### 自治时间增加后需要持续控制与交付核验

OpenAI 的 mid-turn steering 支持在响应运行期间追加用户要求，但不会撤销既有输出或已经启动的工具；待处理 steering 与当前连接相关，需要宿主记录和处理断线。Runifold 已有底层 WebSocket steer 接口，仍需区分它与持久化任务修改的完整契约。[官方 steering 语义](https://developers.openai.com/api/docs/guides/steering)。

用户在任务中途说“只分析，不发布”，应用必须能确认这条更新何时生效、是否使旧计划或旧审批失效，以及更新前已经发生了什么。单纯把新要求追加给模型，无法独立完成这些工作。优先支持工具与轮次边界上的可靠更新；厂商原生 mid-turn 能力通过适配器增强，不能对所有模型承诺相同的中途抢占行为。

## 四 建议形成的产品边界

### 面向已有 Rust 服务的 Agent 执行能力

优先用户是已有 Rust 后端，需要接模型、处理长任务或执行真实业务操作的团队。他们应能逐步使用轻量模型调用、规范 Agent 和 durable workflow，而不必先引入一个强制托管平台。

Runifold 的价值需要落实为具体问题的答案：这个任务是谁授权的，对哪些资源有效，预算剩多少，模型用了哪些材料，哪些操作已发生，断线后从哪里继续，最后交付是否符合要求。

这是一项待验证的定位假设。Rust 的类型和内存安全有实现价值，不能直接证明用户采用、业务安全或更好的 Agent 成绩。单厂商短任务若用直接 SDK 更简单，Runifold 就应保持轻量入口；多模型和持久化不能成为每次使用的前置条件。

### 优先补齐任务控制与外部操作边界

先用一个窄场景验证任务范围授权，例如“在指定项目中创建一条工单”。把租户、资源、动作、参数约束、使用次数、有效期、工具版本和策略版本绑定到当次执行。模型可提出参数与计划，可信应用代码确定授权上限。

读取文档可以影响工单正文，不能自行改变目标项目。审批应绑定实际参数与资源版本，修改目的地、扩大范围或撤销授权后重新校验。不要声称能从任意自然语言自动恢复可靠的字段来源；起点应是宿主提供的结构化选择和显式规则。

执行拦截需要进入规范 callable 与 Effect 路径，并照顾直接工具调用、MCP 和远端适配器。仅在 Agent 外层增加一个 reviewer，不能保证所有执行入口都经过相同策略。权限检查与外部系统实际提交之间仍存在竞争窗口，需要幂等键、资源版本或外部系统支持；取消也不能撤销已提交操作。

授权审批采用有选择的策略：范围内操作直接执行，越界请求明确拒绝或转为待办。持久化待办需要验证重复、过期、跨租户、参数改变和恢复后的回填。Pydantic AI 已有 deferred tools 的公开入口，LangGraph 也有中断与持久化路径，这说明暂停与恢复是需要提供清楚开发体验的基本能力，而非单独的差异化标签。[Deferred Tools](https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/)、[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。

执行与观察需要分离。托管任务的订阅关闭、暂停生成、停止后续动作和取消整个任务应有明确语义。优先复用现有 workflow、事件与信号契约，避免增加另一个竞争调度器。原有由调用方驱动的轻量路径继续保留。

### 用证据约束完成声明

研究助手完成时，应给出结论与来源的关联、待解决的问题和可读取的产物。业务助手完成时，应给出外部服务的操作身份、核对状态及会话提交结果。产物有版本，核验也要绑定版本；旧报告的核验不能认证新报告。

这些证据由可信工具和适配器采集，通过现有事件、Effect 与完成检查关联。模型自己生成一段“执行成功”的 JSON 不算独立证据。哈希可以检测被绑定内容是否改变，不能证明内容真实；日志可以说明适配器报告过什么，也不能单独证明外部世界状态。

事实、假设、来源和待办可以先由参考应用表达，待重复模式出现后再提炼最小公共接口。核心不应直接拥有一套通用研究本体、事实真值数据库或面向所有领域的完成判定器。

### 把持续学习留为可接入方向

MemRL 通过环境反馈更新外部记忆的效用，说明改善 Agent 不只有修改模型权重这一条路径；其附录也承认长轨迹更新方差、贡献分配和任务相似度的限制。[MemRL](https://arxiv.org/html/2601.03192v2)。

短期应把生产失败转成可重复的评估，再比较提示词、工具、上下文策略与模型版本。候选经验经过隔离评估与人工发布后才能影响生产策略，不能自动改写权限或已确认事实。记忆来源、适用任务、版本与失效条件都需要保留。

中期可以提供可选轨迹导出，关联模型请求、调用分支、运行结果、策略版本和奖励。常规脱敏日志不足以直接训练 RL；精确 token、log probability、mask 与训练调度交给训练适配器和外部系统。私有正文、凭据和客户数据不因“支持训练”进入默认日志。

## 五 用应用和实验决定投入顺序

### 第一阶段 完成当前能力验收并建立比较基线

先收敛当前上下文、调度和协议变更，按受影响 crate 的规则完成测试、Clippy、格式与必要的真实服务验收。确认发布内容，再对外描述能力。

参考应用 A 使用公开或合成材料持续研究一个问题：保留材料、产生带来源的判断、接收新证据修正结论，并在上下文溢出、断线和重启后继续。参考应用 B 使用本地模拟业务服务：对指定项目执行一次变更，支持审批等待、提交后确认丢失和状态核对。两者都应无需凭据完成离线验收，并可显式切换到真实服务。

同一任务至少比较直接 SDK 的最小实现、Runifold 单 Agent，以及增加一种策略后的实现。要与其他框架比较时固定模型、工具、预算、语料和终态检查。先看采用 Runifold 减少了哪些胶水代码和故障处理，再看质量或性能收益；不能以单元测试数量替代应用优势。

### 第二阶段 交付任务范围授权与可恢复的人机协作

用业务参考应用做任务参数约束、持久审批、执行监督与事件重连。优先使用确定性规则完成最小闭环，模型 reviewer 作为可选策略比较。

阶段验收应覆盖下表中的前六项。API 只有在恢复身份、提交语义和失效规则明确后才收敛；不为缩短示例而扩大权限。任何新增模块或 crate 都需另行做所有权分析，不由本研究直接触发目录重构。

### 第三阶段 优化上下文工具和预算使用

用研究参考应用比较固定窗口、已有 ContextManager、按引用读取和少量子任务。随后验证动态工具发现、程序化只读批处理，以及更准确的 token 计数。每次只引入可解释的差异，观察质量、时延、成本和故障恢复。

小规模多 Agent 应至少与强单 Agent 和并行工具基线比较。子任务必须有范围、预算、证据与结束条件，但审查深度、路由和通信方式应允许替换。若没有稳定收益，就保留为示例策略，停止扩大 Team API。

### 后续阶段 按实际反馈决定训练接入和部署适配

邀请少量真实 Rust 团队复现两个场景，记录集成时间、重复手写逻辑、部署限制和放弃原因。优先修复反复出现的 DX 问题。只有在任务质量与数据授权稳定后，才进行经验记忆或外部训练接口实验。

部署与沙箱通过边缘适配器接入成熟基础设施。Anthropic 的安全工程案例强调运行环境隔离、凭据隔离和外发控制，也指出可信工具返回仍可能承载提示注入。Runifold 可以规定必须经过的控制点，实际隔离保证由宿主环境与适配器兑现。[Containment 工程案例](https://www.anthropic.com/engineering/how-we-contain-claude)。

### 验收场景与评价指标

| 场景 | 可核验结果 |
| --- | --- |
| 文档要求改写目标项目或收件人 | 对象范围仍由当次授权决定；不发生越界写入 |
| 记忆或子 Agent 声称已有批准 | 不扩张当前授权；合法历史材料仍可用于回答 |
| 变更参数后复用旧审批 | 旧批准失效，恢复也不能绕过检查 |
| 外部操作提交后丢失响应 | 查询得到已提交结果或明确 ambiguous；不无证据重复操作 |
| 审批等待或执行中重启 | 待办身份、参数、策略与预算可核对；回填只应用一次 |
| 用户中途收窄任务范围 | 更新有明确接收与生效状态，后续操作重新校验；保留已发生事实 |
| 客户端断线再订阅 | 不因重连新开模型调用；提交与暂定事件可区分 |
| 大结果或材料超出上下文 | 原文仍可访问，遗漏可解释，不伪称完整阅读或静默截断 |
| 程序或子 Agent 批量调用 | 每次调用均受权限、Effect、预算与取消约束 |
| 声称完成但产物或终态不符 | 完成检查明确失败，报告缺少的证据 |

报告最终任务成功率、重复运行的一致成功、严重违规次数、错误完成率、恢复后终态正确性、成本、P50/P95 时延和人工介入负担。安全违规和数据外泄单独列出，不与质量分加权抵消。样本有限时，“零观察违规”不能表述为“零风险”。

可将优化目标定义为：在明确权限、成本与时延约束下，提高可核验的任务完成率。预算是上限，不是需要花光的目标；某些开放研究任务值得在剩余预算中继续迭代，已满足交付标准的任务则应及时完成。

## 六 投入取舍与反证条件

| 方向 | 当前选择 | 重新评估的条件 |
| --- | --- | --- |
| 新 Provider 与逐项 API 跟进 | 维护目标场景所需能力，保留未知语义和显式降级 | 真实采用因具体缺失能力被阻断 |
| 通用 Swarm 或自动生成大型团队 | 保留小团队实验，不作为主线 | 多类任务在相同成本条件下反复获益 |
| 固定复杂规划与多层模型审查 | 做成可替换策略，按任务启用 | 消融实验显示稳定收益且成本可接受 |
| 核心内置 VM 浏览器或代码沙箱 | 定义边缘控制点，接成熟实现 | 多个应用出现相同适配需求与明确维护能力 |
| 自研通用记忆或训练引擎 | 先接评估、版本和轨迹边界 | 应用数据证明现有策略不足，且有可验证训练收益 |
| 强制托管平台与重型控制台 | 先提供可嵌入运行时和清楚的运维输出 | 设计伙伴明确需要托管能力，并愿承担部署成本 |
| 面向物理机器人控制的实时内核 | 先保留模型与执行环境分离 | 有真实设备、时限和安全验收场景；不得把模型调用延迟当成硬实时保证 |

最需要警惕的产品风险，是继续堆积底层能力，却没有应用能证明这些能力值得被采用。若设计伙伴主要需要一次性结构化提取，就强化轻量调用和 typed output；若他们已有 Temporal 等执行系统，就做好嵌入与适配；若托管厂商在质量、成本和控制要求上都足够好，则 Runifold 应围绕跨系统边界提供价值，而不是复制厂商内部循环。

对定位的持续检验，应是开发者能否更容易把一个真实任务从授权推进到可核验交付，以及发生故障时是否少写了难以验证的补救代码。参考应用和设计伙伴反馈应决定下一轮公共能力，而不是由论文标题直接决定模块数量。
